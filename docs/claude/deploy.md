# Deployment

All deploys are tag-triggered. Push to main does NOT deploy anything. Tag conventions:

| Component | Tag pattern | Example | Workflow | Version file |
|-----------|-------------|---------|----------|-------------|
| Server + admin | `server-*` | `server-1.0.0` | `deploy.yml` | `server/VERSION` |
| Landing page | `landing-*` | `landing-1.0.0` | `deploy-landing.yml` | `landing/VERSION` |
| Config service | `config-*` | `config-1.0.0` | `deploy-config.yml` | `config/VERSION` |
| Admin dashboard | `admin-*` | `admin-1.0.0` | `deploy-admin.yml` | `admin/VERSION` |
| Client apps | `v*` | `v1.36.0` | `release.yml` | `client/package.json` |
| Client (pre-release) | `v*-beta.*` | `v1.36.0-beta.1` | `release.yml` | `client/package.json` |

All workflows also support `workflow_dispatch` for manual trigger from GitHub UI.

**Control plane + exits since 2026-09-15 (PRXNS-19).** Each deploy job is a matrix with `fail-fast: false` (a dead host turns its own leg red and never blocks the others) over:

| target | host | role |
|---|---|---|
| `control` | FirstVDS 157.22.194.55 (`VPS3_HOST` / `VPS3_SSH_KEY`), shared with Ansamblist | **control plane**: admin API + config service + landing + **primary Postgres**. Never in the client's server list, carries no VPN traffic. DNS for `proxyness.smurov.com` + `admin.` points here. Landing publishes **8082** (Caddy owns 80/443). |

Adding an exit = `scripts/vps/push.sh`, `pg-sync.env` pointing at the control plane, two secrets, one matrix line, one entry in the client's `SERVERS` (until PRXNS-21 moves that list into the config).

The container runs under name `proxyness`, pulls `ghcr.io/${{ github.repository }}:latest`, exposes 443 TCP + UDP via the SNI router (TCP on host port 4430, UDP direct on 8443), and reads the Postgres URL from `/etc/proxyness/db.env` via `docker run --env-file`.

The cert is not verified by the proxy transport itself (`InsecureSkipVerify: true` in TCP fallback; UDP transport does its own X25519+HMAC crypto and never sees TLS), so an expired cert doesn't break VPN connectivity — only `/api/sync`, the landing, and anything else that verifies properly.

## Shared infra on Aeza

- **Host nginx** as SNI-based TCP router on port 443. `stream` block peeks SNI hostname: `admin.proxyness.smurov.com` → 127.0.0.1:8444 (TLS terminated by nginx `http` block, Let's Encrypt cert, proxied to admin container on 8081); everything else → 127.0.0.1:4430 (proxy container, handles its own TLS). UDP 443 bypasses nginx (stream is TCP-only). Config: `/etc/nginx/nginx.conf`. Cert renewal: see the **SSL** bullet above (standalone + landing-container hooks; nginx is NOT stopped during renewal).
- **Admin dashboard**: nginx container on Aeza only (`proxyness-admin`, port 8081:80). Deployed via `admin-*` tags. Image built locally on Aeza from `admin/Dockerfile` (until GHCR CI is wired).
- **Host systemd units (NOT in any deploy workflow — install by hand after a rebuild)**. Sources live in `scripts/`, but nothing copies them to a fresh VPS automatically; if the host is ever reprovisioned, reinstall both or they silently stay missing:
  - `cake-ingress.service` (+ `/usr/local/sbin/cake-ingress.sh`) — ingress shaper, see the CAKE bullet in decisions.md. Change the `45Mbit` in `ExecStart` whenever the plan's bandwidth changes.
  - `99-proxyness-tcp.conf` → `/etc/sysctl.d/` (source `scripts/systemd/`) — raises `tcp_max_syn_backlog` from the 128 default to 4096, matching `somaxconn`. Applied 2026-07-30 after `netstat -s` showed 39k "listen queue of a socket overflowed" / 39k "SYNs to LISTEN sockets dropped" over one uptime; see the SYN-drop bullet in decisions.md.
  - `sysstat` — package installed but collection ships **disabled** on Debian (`ENABLED="false"` in `/etc/default/sysstat`). Enabled 2026-07-30 so `sar` has per-minute CPU/network/TCP history; without it a past incident cannot be reconstructed at all.
  - `vnstat-export.timer` / `.service` (+ `/usr/local/sbin/vnstat-export.sh`, source `scripts/vnstat-export.sh`) — every 5 min writes `vnstat --json` to `/var/lib/docker/volumes/proxyness-data/_data/vnstat.json`, which the proxy container reads as `/data/vnstat.json` and serves at `GET /admin/api/bandwidth` for the admin Bandwidth page. Writes to a temp file then renames, so a reader never catches a partial file. **This works only because the export path sits inside the already-mounted `proxyness-data` volume** — pick any other host path and you also have to add a bind mount, which means `docker rm` + fresh `docker run`, not a restart. Override the container-side path with `PROXYNESS_VNSTAT_JSON` if the volume layout ever changes. `vnstat` itself is a plain apt package on the host (`vnstat.service`, enabled); the container has no view of the host NIC and cannot collect this itself.
- **Postgres 16** (pgdg repo) on Aeza only. `listen_addresses = '127.0.0.1,172.17.0.1'` — host loopback for `psql` and tests, plus the docker bridge gateway so the proxy container can reach the host DB from inside the bridge network. NOT public. Cluster `16/main`, restart with `systemctl restart postgresql@16-main` (`listen_addresses` requires restart, not reload). `pg_hba.conf` allows `127.0.0.1/32` and `172.17.0.0/16` via `scram-sha-256`. The proxy container's connection URL lives in `/etc/proxyness/db.env` (mode 600) as `PROXYNESS_DB_URL=postgres://proxyness:<pw>@172.17.0.1:5432/proxyness?sslmode=disable` — **do NOT** use `127.0.0.1` there, that's the container's own loopback, not the host. Reading the env file is one-shot at `docker run --env-file ...` time; if you edit `db.env`, you have to `docker rm` and `docker run` the proxy container, **not** `docker restart` (the latter keeps the old env). Schema source of truth: `server/internal/db/pg/schema.sql` — apply as `proxyness` role (use `SET ROLE proxyness` before `\i schema.sql` if connecting as `postgres`) so tables end up owned by the app role, not `postgres`.
- **One-off SQLite→Postgres migrator** (`server/cmd/migrate-pg/`): copies a SQLite snapshot into Postgres via `pgx.CopyFrom`, re-aligns sequences, filters orphan FK rows, supports `--truncate`. Ran once at cutover (2026-04-16, server-2.0.0); proxy runtime does not use it.
- **Role `proxyness` has `CREATEDB`**: granted for `server/internal/db/db_test.go` which spins a private `proxyness_test_<ns>` per test, applies `pg/schema.sql`, drops at cleanup. `CREATEDB` does NOT grant access to other databases — safe. Tests skip if `PROXYNESS_TEST_DB_URL` is not set (CI does not run these; local dev uses `ssh -L 15432:127.0.0.1:5432 root@aeza` to expose Postgres).

## Provisioning kit (`scripts/vps/`)

Everything a fresh Debian 12/13 box needs to become an exit, idempotent, one command from the Mac:

```bash
scripts/vps/push.sh proxyness2        # rsync scripts/ + schema.sql → /root/proxyness-setup, run vps/provision.sh
```

`provision.sh` does: hostname, 2G swap (RAM < 4G), docker + volumes, Postgres 16 from pgdg (`listen_addresses` loopback + docker bridge, `After=docker.service` drop-in, role/db/schema, random password into `/etc/proxyness/db.env`), self-signed placeholder certs (proxy volume + nginx admin), host nginx SNI router from `vps/nginx.conf`, certbot renewal hooks from `vps/certbot-hooks/`, sysctl (`99-proxyness-tcp.conf` + ip_forward/BBR), vnstat + export timer, sysstat, AmneziaWG module + tools (`vps/awg-install.sh`, DKMS from source — Debian has no PPA), `pg-sync` and `cake-ingress` units (installed, **not** enabled), and finally key-only sshd if `authorized_keys` is non-empty.

After provisioning, by hand and in this order:

1. Add the CI key to `/root/.ssh/authorized_keys` (`~/.ssh/proxyness_ci_deploy.pub` on the Mac; private half = `VPS2_SSH_KEY`).
2. Point DNS at the host, then `vps/issue-certs.sh` (standalone certbot; the pre/post hooks park the landing container).
3. Run the four deploy workflows (`workflow_dispatch`) — they inject the admin credentials, which the kit deliberately never touches.
4. Seed or sync the DB: `vps/seed-device.sh "<user>" "<device>" <key>` for a bootstrap, or make it a secondary (below).
5. `vps/awg-migrate-peers.sh <dir-with-client-confs>` — rebuilds `awg0.conf` from client configs, writes re-pointed confs + QR PNGs to `/root/awg-clients/`.

**Secondary / primary.** The primary is where the admin panel writes. On a secondary: `echo PRIMARY_SSH=proxyness-primary > /etc/proxyness/pg-sync.env` (an ssh alias whose key the primary's root accepts), `systemctl enable --now proxyness-pg-sync.timer`. It pulls `users, devices, sites, site_domains, site_ips, user_sites, changelog` every minute (upsert by PK, delete rows gone from the primary, children first); `traffic_stats`/`logs` stay local. Swapping roles = move that env file and the timer to the other box, repoint the admin's `VITE_API_URL`/DNS.

**Runbook: Serverspace comes back after 2026-09-15.** (1) `ssh proxyness` — confirm containers, then `pg_dump -d proxyness --data-only -t users -t devices -t sites -t site_domains -t site_ips -t user_sites` — this is the real user base, Aeza only has seeded devices. (2) Import into Aeza (upsert; device keys are unique so seeded rows for the same key are updated in place, not duplicated). (3) Install `proxyness_ci_deploy.pub` and `proxyness2_smurov.pem.pub` in Serverspace's `authorized_keys` — its CI leg uses the old `VPS_SSH_KEY`, which still works, but the Mac alias `proxyness` keeps its own key. (4) Decide the primary; enable `proxyness-pg-sync.timer` on the other one. (5) Certs: whichever host DNS does **not** point at cannot renew via HTTP-01 — copy `/etc/letsencrypt/live/*` from the DNS host by cron or accept that its landing/`/api/sync` cert goes stale (the proxy transport does not care). (6) AmneziaWG: keep both server keys; phones can hold both configs.

## Control plane on the shared FirstVDS box (PRXNS-19)

Why: the 2026-09-15 outage showed the only copy of users/devices living on an exit that can be lost or blocked. The control plane lives in RU (RU→RU is never DPI-blocked, so clients always reach the config), exits abroad are disposable replicas. Ilya's call; a dedicated small VPS is the planned next step.

- **Box**: Ubuntu 24.04, `root@157.22.194.55` (key auth from the Mac, no alias yet), `/root/ansamblist` = git checkout of `ilyasmurov/Ansamblist`, its compose stack owns 80/443 through `ansamblist-caddy-1`. Ansamblist deploys only via `workflow_dispatch` (git pull + compose on the box).
- **Routing**: `deploy/Caddyfile.ansamblist` in the Ansamblist repo — `proxyness.smurov.com`: `/api/*`, `/admin/*`, `/health` → `https://172.17.0.1:4430` (proxy container, self-signed, `tls_insecure_skip_verify`, `flush_interval -1` for SSE), everything else → `172.17.0.1:8082` (landing); `admin.proxyness.smurov.com` → `172.17.0.1:8081`. Caddy issues the public certs itself. Apply: commit in the Ansamblist repo, `git pull` in `/root/ansamblist`, then **`docker restart ansamblist-caddy-1`** (2–3 s blip for every site on the box) — NOT `caddy reload`: the Caddyfile is a single-file bind mount, `git pull` writes a new inode, and the container keeps seeing the old file (`caddy reload` answered "config is unchanged" on 2026-09-15 until the restart; `docker exec … grep proxyness /etc/caddy/Caddyfile` shows which file the container has). Do it **only after DNS points here**, otherwise Caddy burns ACME failed-validation quota. Certs land in ~20 s (`docker logs ansamblist-caddy-1 | grep 'certificate obtained'`). Proxyness containers are on the default docker bridge, hence `172.17.0.1`; the proxy binary's own landing reverse-proxy to `172.17.0.1:80` would hit Caddy and loop, which is why Caddy does the path split instead.
- **Bootstrap**: `scripts/vps/control-plane-shared.sh` (via `push.sh <host> sync-only`) — volumes, `proxyness-pg` (postgres:16-alpine, `127.0.0.1:5433` + `172.17.0.1:5433`, volume `proxyness-pg-data`), schema, `/etc/proxyness/db.env` with `172.17.0.1:5433`, cert placeholder. Waits for the *real* Postgres (the image runs a throwaway server during first init — `pg_isready` answers for it).
- **Replica on an exit**: `/etc/proxyness/pg-sync.env` = `PRIMARY_SSH=root@157.22.194.55` + `PRIMARY_PSQL="docker exec -i proxyness-pg psql -U proxyness -d proxyness"`; the exit's root key is in the control plane's `authorized_keys`; `systemctl enable --now proxyness-pg-sync.timer`. Pulls users, devices, sites, site_domains, site_ips, user_sites, changelog; upsert by PK (tables whose PK is every column use `DO NOTHING`), delete rows gone from the primary, children first. `traffic_stats`/`logs` stay local. Verify: `journalctl -u proxyness-pg-sync -n 3`.
- **Config service callback** is `-proxy https://127.0.0.1:4430` on every host (an IP URL carries no SNI for Caddy to route on).
- **Known gap**: the admin dashboard on the control plane shows zero traffic — stats are counted by the process that carries traffic. Aggregation from exits is a separate task.

## Taskless egress proxy rides on the Aeza exit (since 2026-09-15)

Taskless prod (Yandex Cloud, `taskless-new` = 81.26.185.252) reaches Anthropic (403 from RU) and Telegram (blocked from RU) through an HTTP forward proxy on our exit box — it lived on Serverspace, now on **Aeza 178.236.252.28**: `tinyproxy` 1.11.2 on `:3128` (ACL `Allow` 127.0.0.1 / 81.26.185.252 / 157.22.194.55) plus the metrics exporter `tinyproxy-exporter.service` on `:9128` and `tinyproxy-firewall.service` (iptables: both ports open only to those hosts, `Environment=PROD_IP=… LEGACY_PROD_IP=…` in the unit; rules also saved via `netfilter-persistent`). The exporter and firewall script are the versioned copies from the **Taskless repo** `deploy/egress-proxy/`; the tinyproxy config is hand-written on the box (`/etc/tinyproxy/tinyproxy.conf`). **`scripts/vps/provision.sh` does not install any of this** — re-provisioning the exit means redoing it by hand (or add it to the kit). When the exit's IP changes: Taskless prod `.env` (`/root/taskless/deploy/.env`, root-only, `sudo` as `ubuntu`) `ANTHROPIC_HTTPS_PROXY` + `TELEGRAM_HTTPS_PROXY`, then `sudo docker compose --project-directory /root/taskless/deploy -f …/docker-compose.prod.yml --env-file …/.env up -d --force-recreate --no-deps api` — the Telegram worker lives inside `api`. Verify from inside: `docker exec deploy-api-1 sh -c 'curl -x "$ANTHROPIC_HTTPS_PROXY" -o /dev/null -w "%{http_code}" https://api.anthropic.com/v1/models'` → 401. Note: `docker-compose.prod.yml` does not pass `EGRESS_PROXY_METRICS_URL` to `api`, so the admin "resources" tab cannot see the exporter until that is added on the Taskless side.

## RU bridge to the Aeza exit (PRXNS-22)

Ilya's home ISP (SkyNet, SPb) completes the TCP handshake to `178.236.252.0/24` but drops every data packet, TCP and UDP alike (its own router answers ICMP admin-prohibited); mobile data and Yandex Cloud reach Aeza fine. Rather than gamble on Aeza's "change IP", the client gets a **bridge**: the Taskless prod box in Yandex Cloud (`taskless-new`, public 81.26.185.252, private 10.130.0.24) DNATs `4443/tcp → 178.236.252.28:443`, `8443/udp → :8443` and `13337/udp → :13337` (AmneziaWG). Script `/usr/local/sbin/proxyness-bridge.sh` + `proxyness-bridge.service` (oneshot, idempotent `-C || -I`, ACCEPT both directions in `DOCKER-USER`, per-port MASQUERADE, `ip_forward`). TCP sits on 4443 because 443 there is Caddy for taskless.ru; the daemon always dials UDP on 8443 whatever port the address carries, so `81.26.185.252:4443` works as a plain `SERVERS` entry ("Aeza via RU", 1.46.1). Crypto stays end-to-end daemon↔Aeza; the bridge only NATs and sees the exit as the only destination. **Yandex Cloud security group must allow inbound 4443/tcp, 8443/udp, 13337/udp** — the rules are on the VM, the SG is in the console (no `yc` CLI on the Mac). Only Ilya's home uses it; everyone else dials Aeza directly. Moving it to a dedicated VM = same script, new IP in `SERVERS` (or in the config once PRXNS-21 lands). AWG "via RU" client configs/QRs (same keys, endpoint `81.26.185.252:13337`) live in `~/Desktop/aeza-amneziawg/via-ru/` and on Aeza in `/root/awg-clients/via-ru/`.
